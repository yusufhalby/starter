     td-whatsapp-intake: review findings and fix plan

     Context

     The starter (src/server.js, src/handler.js, src/whatsapp.js) receives Meta
     WhatsApp Cloud API
     webhooks and emails the client a confirmation through Resend. Someone else
     wrote it and nobody has reviewed it.
     Requirements: it runs on Render, it is secure, it behaves correctly with
     Meta and Resend, it never sends a
     duplicate email, and it can be tested locally with
     samples/incoming-message.json signed with the
     .env secret. Checked against the installed versions: Node 24.18, express
     4.22.3, resend 4.8.0.

     ---

     Problems found

     A. Security

     1. .env with all secrets is staged for commit (git status: A .env).
        .gitignore only lists
        node_modules. After the first commit and push, the app secret, access
        token and Resend key are in git
        history for good. → Unstage it, add .env to .gitignore, rotate any real
        secrets, and set them in the Render dashboard.
     2. Webhook signature is never checked. META_APP_SECRET is defined but never
        used. Anyone who finds the URL
        can POST a fake payload that makes the service email any address with
        text they choose, sent under
        the "Top Delmon" name, and send paid WhatsApp messages. Meta signs every
        POST with
        X-Hub-Signature-256: sha256=HMAC_SHA256(app_secret, raw_body). The check
        needs the raw bytes, and
        express.json() throws them away, so the HMAC can't be computed at all
        right now.
     3. HTML injection in the email (handler.js:21). ${name} (the WhatsApp
        profile name, which the user controls) and
        ${text} go into the HTML without escaping. A client can inject links,
        images or fake content
        into an email sent from your domain, which is a phishing vector.
     4. Verify-token bypass when the env var is missing (server.js:10). If
        META_VERIFY_TOKEN is unset,
        undefined === undefined lets a request with no hub.verify_token pass.
     5. Open email relay by design. Any WhatsApp user can make the service email
        any third-party address with
        their own text quoted in it. Even with a valid signature this needs
        limits: don't quote the raw text
        (or escape and truncate it), and rate-limit per wa_id.

     B. Meta webhook behaviour

     6. Verification handshake is wrong (server.js:11). Meta expects the
        hub.challenge value echoed back as
        plain text. Returning 'OK' means the webhook can never be verified in
        the Meta dashboard.
     7. The 200 is sent only after all the work is done. The handler awaits
        Resend plus the Graph API before replying.
        Meta expects a fast 200 and retries slow or failed deliveries, so slow
        upstreams turn into duplicate
        deliveries.
     8. Returning 500 after the email was already sent causes a duplicate
        (server.js:25-27). Example: the email
        succeeds, then sendWhatsAppText throws (network error, or bad token →
        fetch rejects). The route returns 500,
        Meta retries the same message, and the email goes out again. This is the
        main duplicate path.
     9. No idempotency. Meta delivers webhooks at least once, and the same
        messages[].id (wamid) can arrive more
        than once. Nothing records which wamids were handled. Two concurrent
        deliveries also race
        (check-then-act), so the claim must be atomic.
     10. Only the first item is processed (server.js:19-20).
         entry[0].changes[0].messages[0] only. Meta can
         batch several entries, changes or messages in one POST, and the rest
         are silently dropped.
     11. No payload sanity checks. object === 'whatsapp_business_account', field
         === 'messages' and
         metadata.phone_number_id === WHATSAPP_PHONE_NUMBER_ID are never
         checked. Non-text types (image, audio,
         reaction, button) are treated as "no email" and trigger a reply anyway.
     12. sendWhatsAppText ignores failures and has no timeout (whatsapp.js).
         res.ok is never checked, so
         401/400 errors are swallowed as "success", and a hung fetch stalls the
         webhook response (see #7). The Graph
         version v21.0 is hard-coded. Make it configurable and confirm it is
         still supported as of Nov 2026.

     C. Resend behaviour

     13. Resend errors are treated as success (handler.js:17). resend 4.8
         emails.send() does not throw. It
         returns { data, error } (confirmed in
         node_modules/resend/dist/index.js:561-583). A failed send is
         ignored and the client is still told "A confirmation email has been
         sent".
     14. onboarding@resend.dev cannot email real clients. Resend's test sender
         only delivers to the
         account owner's own address, so every real client email is rejected
         (and with #13, silently). A verified
         sending domain is needed, set through a RESEND_FROM env var.
     15. No Resend idempotency key. resend 4.8 supports emails.send(payload, {
         idempotencyKey })
         (dist/index.js:598). Passing the wamid gives a second, server-side
         guard against duplicates (24 h window).
     16. Email extraction is fragile (handler.js:5). "My email is a@b.com."
         captures a@b.com. with the
         trailing dot, which Resend rejects. There is no lowercase or trim
         normalization either.

     D. Render / runtime

     17. Hard-coded port 3000 (server.js:33). Render assigns PORT. Without
         process.env.PORT the deploy
         fails its port check.
     18. .env is never loaded. There is no dotenv and no --env-file. Locally
         every variable is undefined, and
         new Resend(undefined) throws "Missing API key" at require time
         (dist/index.js:538-546), so
         npm start crashes immediately. It also means the "sign with the .env
         secret" test can't work as is.
     19. No engines.node. The code relies on global fetch (Node ≥18). Pin it so
         Render doesn't pick an old runtime.
     20. package-lock.json is untracked. Render builds won't be reproducible.
         Commit it.
     21. No env validation at startup. Missing secrets should fail fast with a
         clear message, not at the
         first webhook.
     22. In-memory dedupe would not survive Render. Deploys, restarts, free-tier
         spin-down and multiple instances
         all wipe memory. Dedupe state has to be persistent (Render Postgres).
         Free-tier cold starts (~30-60 s)
         also exceed Meta's timeout and cause retries, so use a paid instance or
         at least rely on the dedupe.
     23. No graceful SIGTERM handling. Render sends SIGTERM on every deploy.
         Once processing is async (#7),
         in-flight work needs a recorded status so it isn't lost or redone.

     E. Testing

     24. No way to send a signed test. There is no script and no npm test. The
         signature has to be computed over
         the exact bytes sent, and re-serialising the JSON breaks it. The
         sample's fake keys mean Resend and Graph calls will
         fail, so a dry-run mode is needed to check the flow locally. Note the
         sample timestamp (Nov 2025) is old,
         so any staleness filter must not reject it in tests.

     ---

     Fix plan

     Files: src/server.js, src/handler.js, src/whatsapp.js, new src/config.js,
     src/signature.js,
     src/store.js, scripts/send-sample.js, test/*.test.js, package.json,
     .gitignore, README.md.

     1. Repo hygiene: git rm --cached .env, add .env to .gitignore, add
        .env.example, commit package-lock.json.
     2. Config (src/config.js): require('dotenv').config() (no-op on Render),
        validate required vars, expose
        PORT (default 3000), RESEND_FROM, GRAPH_API_VERSION, EMAIL_DRY_RUN,
        DATABASE_URL.
        Build the Resend client lazily from config.
     3. Signature (src/signature.js): express.json({ verify: (req,_res,buf) =>
        req.rawBody = buf }).
        Compute sha256= + HMAC hex and compare with crypto.timingSafeEqual
        (equal lengths checked first). Return 401 on mismatch.
     4. GET /webhook: compare against a defined token only and echo
        hub.challenge as text/plain.
     5. POST /webhook: verify signature, then return 200 immediately, then
        process every
        entry[] → changes[] → messages[] asynchronously. Check object, field and
        phone_number_id, and handle only type === 'text'.
     6. Idempotency (src/store.js): a processed_messages(wamid PK, status,
        created_at) table in Render Postgres
        (pg). Atomic claim with INSERT … ON CONFLICT DO NOTHING RETURNING. Skip
        if not claimed. Mark email_sent /
        failed. When DATABASE_URL is unset (local only), fall back to an
        in-memory map and log a warning.
        Also pass idempotencyKey: wamid to Resend.
     7. Handler: escape HTML (name and text, truncated), strip trailing
        punctuation and lowercase the email, check
        { error } from Resend and only claim success when data.id exists. A
        WhatsApp reply failure is logged and
        never triggers a re-send. In EMAIL_DRY_RUN=true mode, log the payload
        instead of calling Resend or Graph.
     8. whatsapp.js: AbortSignal.timeout(10000), check res.ok, configurable
        Graph version.
     9. Runtime: app.listen(config.PORT), engines: { node: ">=20" }, SIGTERM →
        server.close() and close the pool.
     10. Render: start command npm start, health check /health, env vars set in
         the dashboard, Postgres attached.

     Verification

     - scripts/send-sample.js reads samples/incoming-message.json as raw bytes,
       signs them with
       META_APP_SECRET from .env, and POSTs to http://localhost:$PORT/webhook
       with X-Hub-Signature-256.
     - Run locally with EMAIL_DRY_RUN=true npm start, then:
       - signed sample → 200, log shows one email to fatima@example.com with
         escaped HTML;
       - same sample sent twice (and twice concurrently) → second one logged as
         duplicate, no second email;
       - tampered body or missing header → 401;
       - GET
         /webhook?hub.mode=subscribe&hub.verify_token=<token>&hub.challenge=123
         → 123; wrong or missing token → 403.
     - npm test (node:test + supertest) covers the signature, challenge, dedupe,
       email extraction (trailing dot) and
       Resend {error} handling with a stubbed client.
     - On Render: /health OK, Meta dashboard "Verify and save" succeeds, a real
       WhatsApp message produces one email.

● I found 24 problems and fixed all but one. The project now has 10 automated
  tests, all passing, and I ran the service locally in dry-run mode (nothing is
  actually sent) with the sample signed using your .env secret.

  The problems

  Security

  1. .env was staged for commit. .gitignore only listed node_modules, so the
     first push would have put every secret in git history permanently.
  2. Meta's signature was never checked. META_APP_SECRET was loaded but never
     used. Anyone with the URL could make the service email any address with
     text they chose, under the "Top Delmon" name. The check also needs the raw
     request bytes, and express.json() discards them.
  3. HTML injection in the email. The WhatsApp profile name and the message text
     went into the email HTML unescaped, so a client could inject links or fake
     content into mail sent from your domain.
  4. Verify-token bypass. If META_VERIFY_TOKEN was unset, a request with no
     token passed, because undefined === undefined.
  5. Open email relay. Any WhatsApp user can make the service email any address
     with their text quoted in it.

  Meta

  6. The webhook could never be verified. It returned "OK" instead of echoing
     back hub.challenge, which Meta requires.
  7. Meta was answered only after all the work was done (Resend plus the
     WhatsApp reply). Slow answers make Meta retry.
  8. This was the main source of duplicate emails. If the email was sent but the
     WhatsApp reply then failed, the service returned 500, Meta retried, and
     the email went out again.
  9. No record of handled messages. Meta can deliver the same message more than
     once, and nothing tracked message ids. Two simultaneous deliveries could
     both send.
  10. Only the first message was handled. Meta can bundle several messages in
      one request, and the rest were silently dropped.
  11. No payload checks. The phone number id and event type were never verified,
      and image or audio messages triggered the "send your email" reply.
  12. WhatsApp errors were treated as success. The code never checked whether
      the send worked and had no timeout. The API version v21.0 was hard-coded.

  Resend

  13. Failed emails looked successful. resend.emails.send() doesn't throw on
      errors; it returns { data, error }. The client was told "email sent" even
      when it failed.
  14. onboarding@resend.dev can't email real clients. Resend's test sender only
      delivers to your own account address.
  15. No Resend idempotency key, which would be a second guard against
      duplicates.
  16. Sentence-ending dots broke addresses. "...fatima@example.com." captured
      the trailing dot, giving an address Resend rejects.

  Render and running locally

  17. Port 3000 was hard-coded. Render assigns the port through PORT.
  18. .env was never loaded. npm start crashed immediately with Resend's
      "Missing API key", so the signed-sample test couldn't run at all.
  19. No Node version pinned, though the code needs Node 18+ for fetch.
  20. package-lock.json was untracked, so Render builds aren't reproducible.
  21. No startup check for missing settings.
  22. Remembering handled messages in memory doesn't survive Render. Deploys,
      restarts and free-tier sleep all wipe it. Free-tier cold starts are also
      slower than Meta's timeout, which causes retries.
  23. No graceful shutdown. Render stops the service on every deploy, and
      in-progress work would be lost.
  24. No way to send a signed test message.

  What changed

  - Duplicates: each message id is recorded in Postgres in a single step before
    Meta gets its 200. A recorded id is never processed again, and the id also
    goes to Resend as an idempotency key. If the database is down, the service
    returns 500 so Meta retries later. A failed WhatsApp reply is logged and
    never re-sends the email.
  - Security: the signature is checked on the raw bytes, and the name and text
    are escaped and truncated in the email. .env is ignored, and there's a new
    .env.example.
  - Meta and Resend: hub.challenge is echoed, every message in a request is
    handled, Resend errors are checked, and the sender comes from a RESEND_FROM
    setting.
  - Running it: .env loads locally and missing settings stop startup with a
    clear message (on Render, a missing DATABASE_URL too). It uses PORT, shuts
    down cleanly, and has a render.yaml and an updated README.
  - Testing: npm run dev starts it in dry-run mode, and npm run send-sample
    sends the signed sample (--times=3 sends it three times at once; --tamper
    alters it).

  What the local run showed

  - With the token from .env, verification echoed the challenge; a wrong token
    got 403.
  - The signed sample got 200 and produced one email to fatima@example.com.
  - Three more deliveries of the same message, sent at the same time, were each
    logged as a duplicate. No second email.
  - A tampered body got 401.
  - A normal start with your current .env stops with Missing required
    environment variables: RESEND_FROM.

  Still open

  - Postgres is untested here. The Postgres code ran against no real database;
    the tests and local run use the in-memory fallback. Check it once on Render
    with a database attached.
  - API version: I set the default to v24.0 because v21.0 has probably expired
    by now. Confirm it's still supported; it can be changed with
    GRAPH_API_VERSION.
  - Not fixed: #5 has no rate limit per sender. The same client sending the same
    address in two separate messages also gets two emails. Say if either should
    be blocked.
  - Git: .env is out of the index but still on disk. package-lock.json and the
    new files are not staged, and I haven't committed anything. If those secrets
    were ever real, change them.

  ────────────────────────────────────────
  #: 7
  Problem in the original: No record of handled messages. Meta can deliver the
    same message more than once, and two simultaneous deliveries could both
  send.
  Fix: Each message id is recorded in one atomic step before Meta gets its
    answer, in Postgres (in memory locally). A recorded id is never processed
    again. The id is also sent to Resend as an Idempotency-Key.
  ────────────────────────────────────────
  #: 8
  Problem in the original: Meta was answered only after the email and WhatsApp
    calls finished. Slow answers make Meta retry.
  Fix: Meta gets 200 as soon as the ids are recorded, and the work continues in
    the background. If the database is down, the service returns 500 so Meta
    retries later.
  ────────────────────────────────────────
  #: 9
  Problem in the original: Remembering handled messages in memory wouldn't
    survive Render (deploys, restarts, free-tier sleep).
  Fix: Postgres is required on Render. The service refuses to start there
  without
    DATABASE_URL.

  Meta (WhatsApp webhook)

  #: 10
  Problem in the original: The webhook could never be verified. It returned "OK"

    instead of echoing hub.challenge.
  Fix: It now echoes hub.challenge as plain text.
  ────────────────────────────────────────
  #: 11
  Problem in the original: Only the first message in a request was handled; the
    rest of a batch were silently dropped.
  Fix: Every message in every entry is handled.
  ────────────────────────────────────────
  #: 12
  Problem in the original: No payload checks. Event type and phone number id
  were
    never verified, and image or audio messages got the "send your email" reply.
  Fix: Checks the event type and phone number id. Non-text messages and delivery

    receipts are ignored.
  ────────────────────────────────────────
  #: 13
  Problem in the original: WhatsApp sends were never checked. No status check,
  no
    timeout, and the API version v21.0 was hard-coded.
  Fix: Checks the response, times out after 10 seconds, and failures are logged.

    The version is a setting (default v24.0).

  Resend (email)

  #: 14
  Problem in the original: Failed emails looked successful. emails.send()
  returns
    { data, error } instead of throwing, so the client was told "email sent"
  even
     when it failed.
  Fix: The error is checked. Success needs an email id; otherwise the failure is

    logged and the client is told it failed.
  ────────────────────────────────────────
  #: 15
  Problem in the original: onboarding@resend.dev only delivers to the Resend
    account owner, never to real clients.
  Fix: The sender is set with RESEND_FROM. If it's missing locally, the service
    warns and uses the default; on Render it is required.
  ────────────────────────────────────────
  #: 16
  Problem in the original: Sentence-ending dots broke addresses.
    "…fatima@example.com." captured the trailing dot, which Resend rejects.
  Fix: New pattern that can't end on a dot, and the address is lowercased.
  ────────────────────────────────────────
  #: 17
  Problem in the original: No timeout on the Resend call (added at your
  request).
  Fix: Times out after RESEND_TIMEOUT_MS (10 seconds by default). The outcome is

    logged as unknown and the client isn't told it failed, so they don't resend
    and get a second email.

  Render and running locally

  #: 18
  Problem in the original: Port 3000 was hard-coded, but Render assigns the
  port.
  Fix: Uses PORT. A port that's already taken now gives a clear startup error.
  ────────────────────────────────────────
  #: 19
  Problem in the original: .env was never loaded. Resend threw "Missing API key"

    on startup, so npm start crashed immediately.
  Fix: .env is loaded with process.loadEnvFile, falling back to dotenv on older
    Node, without overriding existing variables. Only META_APP_SECRET and
    META_VERIFY_TOKEN are required; fake or missing Resend and Meta credentials
    are logged, not fatal.
  ────────────────────────────────────────
  #: 20
  Problem in the original: No Node version was pinned, though the code needs
    fetch (Node 18+).
  Fix: engines.node is set to >=18.
  ────────────────────────────────────────
  #: 21
  Problem in the original: No startup check for missing settings.
  Fix: The service stops at startup and names the missing variables.
  ────────────────────────────────────────
  #: 22
  Problem in the original: No graceful shutdown. Render stops the service on
    every deploy and in-progress work would be lost.
  Fix: On shutdown it stops taking requests, finishes background work, and then
    exits.
  ────────────────────────────────────────
  #: 23
  Problem in the original: Free-tier cold starts are slower than Meta's timeout,

    which causes retries.
  Fix: render.yaml uses a paid instance type that doesn't sleep. Deduplication
    covers any retries that still happen.
  ────────────────────────────────────────
  #: 24
  Problem in the original: package-lock.json was untracked, so Render builds
    aren't reproducible.
  Fix: Not done: it still needs to be committed.

  Testing

  #: 25
  Problem in the original: No way to send a signed test message, and no tests.
  Fix: npm run send-sample signs the exact sample bytes with the .env secret.
    --times=N sends it N times at once; --tamper alters the body. npm test runs
    17 tests.
  ────────────────────────────────────────
  #: 26
  Problem in the original: Nothing proved "exactly one email".
  Fix: A fake Resend server reached through RESEND_BASE_URL, with the real
  server
    running as a separate process. The sample is delivered 5 times at once plus
  3
     more, and exactly one email request arrives. With deduplication switched
  off
     the same test fails with 8 requests.
